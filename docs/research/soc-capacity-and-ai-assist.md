Prompt injection via log content — the defence and the lesson\n\n**The threat, stated precisely:** security logs are records of adversarial interaction. HTTP URIs, User‑Agent strings, POST bodies, DNS names, attempted usernames — all are written by the attacker. When those fields reach an LLM's context, **the attacker controls part of the prompt.** This lab has kali‑01 firing at ubuntu‑app‑01 on a schedule, so it is not hypothetical here; it is a Tuesday.\n\n**Measured severity** (arXiv 2605.24421, gpt‑4o‑mini, 6 attacker‑controllable fields, 120 malicious logs per condition):\n\n| Attack class | Classification | **Summarisation** | Remediation |\n|---|---|---|---|\n| S1 direct override (\"ignore previous instructions\") | 0% | 0–15% | 1–9% |\n| S2 persona hijack | 15–68% | 24–49% | 11–34% |\n| S3 context manipulation | 16–22% | **96%** | 8–39% |\n| S4 obfuscated payload | 0% | 0% | 0% |\n\nAverage injection success: **26.6% undefended → 11.8% under the strongest defence.** Summarisation — precisely what a triage copilot does — is the most vulnerable task at 96% undefended and still 38% with constrained output. LevelBlue/SpiderLabs demonstrated the concrete version: injection through the USERNAME/DOMAIN fields of a **Windows Event ID 4625** silently rewrote the workstation name and source IP in the AI's summary. **You already have 4625 auditing on win‑client‑01 and Wazuh rules asserting on it.**\n\n**How to handle it — five controls, in order of effect:**\n\n1. **Constrained templated output.** Force the model to emit a fixed JSON schema with enum verdicts and field‑level extraction, never free prose. This is the single measured defence (26.6% → 11.8%; summarisation 96% → 38%). `ai/validators.py` already exists as the static gate — extend it to reject any output not matching the schema.\n2. **Label attacker‑controlled fields explicitly in the prompt.** Wrap `user_agent`, `http_uri`, `auth_user`, `dns_query`, `raw_message` in delimiters with a standing instruction that content inside them is untrusted data, never instruction. Cheap, partial, worth doing.\n3. **Least authority.** Nothing the model drives can close an alert, suppress a rule, or invoke active response. An LLM with authority to act on attacker‑influenced input is a demonstrated path to attacker‑controlled response. OpenSec (arXiv 2601.21083) found IR agents systematically overconfident under adversarial evidence — they proceed to conclusions rather than deferring.\n4. **Read‑only, curated corpus.** The RAG index contains runbooks, ATT&CK and rule documentation. It never ingests raw alert text into the persistent index.\n5. **Ground truth is the SIEM, not the assistant.** Note the trap already latent in `ai/prompts/assistant_system.txt`: it tells the model the repo docs *are* the ground truth. For investigation work they are not — the indexer is. Teach that distinction explicitly or students will read a correct citation as a correct answer.\n\n**Say plainly in the docs: none of this gets injection to zero. 11.8% residual is the best measured figure. The mitigation that actually works is a human who checks the alert.**\n\n**The teachable moment — build this as scenario #4, and it is nearly free.** kali‑01 embeds a prompt‑injection payload in an HTTP User‑Agent hitting ubuntu‑app‑01; nginx logs it; the Wazuh agent forwards it; rules **31164 / 31106** fire exactly as they already do in the proven web‑sqli scenario; the student's `triage` tool summarises the alert and produces a wrong verdict.
