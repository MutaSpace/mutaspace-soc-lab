BROWSER ACCESS — ONE APPROACH\n\n### Decision: Apache Guacamole on `jumpbox-01`, with xrdp multi-session on `analyst-01`.\n\nApache-2.0, clientless HTML5, RDP/VNC/SSH, 1.6.0 (June 2025). LDAP extension binds against `dc-01`/mutaspace.local; JDBC/Postgres extension holds connection permissions (the docs support layering exactly this way). One identity per student across AD, the Windows endpoints and the gateway.\n\n**On `jumpbox-01` specifically because it is already outside the snapshot-reset plane.** If the gateway rolled back with the lab, every student would be disconnected mid-class and the connection database would revert.\n\n### Why not the alternatives\n\n- **Proxmox noVNC deep-links** — the plan already written into `docs/proposals/cyberlab-engine-reuse.md`, and the codex review flagged the hole (`cyberlab-engine-reuse.codex-review.md:64`) without anyone closing it. **It does not work.** The browser console flow needs a real `PVEAuthCookie` session *plus* a `vncproxy`-minted ticket consumed within ~10 seconds, on the same domain to survive anti-CSRF; an API token alone is insufficient. So it resolves to either giving 20–40 students accounts on the **hypervisor management plane** — the one network your own secrets policy treats as secret — or writing a privileged websocket proxy. And it gives *one shared framebuffer per VM*: no isolation, no recording. Kill this plan explicitly. Keep exactly one Proxmox console path: the instructor's break-glass access.\n- **A bespoke websockify/noVNC broker** (porting `vnc_proxy.go`) — worst possible fit for a solo maintainer: you become the owner of a security-critical proxy. Cloudflare **Tunnel** *is* a good optional pairing for remote students (outbound-only, no inbound port, Zero Trust free tier covers 50 users) — but it makes Cloudflare an availability dependency during a live class. Optional, not core.\n\n### How 20–40 students share it — tier the access\n\nGuacamole's concurrency limits (`postgresql-absolute-max-connections`, `postgresql-default-max-connections-per-user`) only **queue and deny**; they ration, they do not isolate. ASSESSMENT AND LMS\n\n### The finding that settles the attribution question\n\nAcross every serious practical assessment reviewed — OSCP, GIAC CyberLive, Locked Shields, CPTC, Splunk BOTS, KYPO — **nobody attributes work by watching the shared infrastructure. Attribution is always done at an identity-bound submission channel, and the environment is only the evidence source.**\n\nThat reframes the problem entirely. You do not need to make one shared lab attributable. You need a **per-student submission object** — the case — and enough per-student telemetry to auto-grade the machine-checkable parts and flag collusion for human review. Cases are **non-rival**: twenty students can each open a case on the same alert and each be scored on their own reasoning.\n\n### The hard limit, stated plainly\n\n**Anything that changes shared lab state cannot be individually scored.** The first student who blocks 10.10.20.10 on fw-01 takes the point and destroys the task for everyone else. This is why the CCDC/Locked Shields availability-scoring family does not port here at all. If you want to assess remediation skill, do it as a scheduled solo exercise on a snapshot that student owns for their slot — a separate assessment type, not part of the shared shift.\n\n### The identity chain (build this first, it is upstream of everything)\n\nGuacamole account → AD account → OS session on `analyst-01` (auid survives sudo) → per-student Wazuh indexer user → portal account. One chain. No shared logins anywhere. Every gradable act carries a student FK **at write time** — if attribution is not captured at the moment of the action, no grade-passback protocol can invent it later.\n\n### Scoring a skills exam from evidence the environment already produces\n\n**1. The answer key you already own.** `scenarios.yml` declares `attack: T1110`, `origin`, `target`, and per-alert `rule_id` + `data.srcip` + `agent.name`, all confirm-on-host. Those are *exactly* the fields a triaging analyst must report. An `answer_key:` block gives you auto-graded detection scoring with **zero new ground-truth authoring**, and because the same file gates the runner's assertions, the answer key can never drift from what actually fired.\n\nThis is your genuine advantage over both real SOCs and commercial ranges. MITRE lists true/false-positive ratio as a core metric that real SOCs can only *estimate*, because they never know full truth. You do.\n\n**2. Score detection depth, not found/not-found.** Use MITRE ATT&CK Evaluations' published ladder — None → Telemetry → General → Tactic → Technique. It maps one-to-one onto the answer key: found the raw nginx 404 burst = Telemetry; named srcip + agent = General; named rule.id + T1110 = Technique. In a quiet lab, \"did they find it\" is not a discriminator; depth of characterisation is.\n\n**3. MTTD, weighted and capped.** `scenario_run_started_at` minus case-creation time. Completely non-rival. Formative during shifts; summative only inside a time-boxed exam.\n\n**4. Anti-gaming counterweights — non-negotiable.** Assessment is the point of the product, so students will optimise for the gradebook harder than analysts optimise for the SLA. MITRE ships the controls: report **median and percentiles, never mean** (\"a single missed incoming email… can demolish a mean time to respond\"); pair every speed metric with **alert follow-up ratio** (escalations later confirmed TP, target ~25%) and **alerts not investigated** (closed with no query run, target <25%). That second one is directly computable by joining case-close events against indexer audit logs — a query, not a subsystem — and it is the sharpest cheating detector you will get. Also: Locked Shields found report *quantity* was not quality (\"BT5 obtained a higher score with a smaller number of reports\"). Unweighted speed scoring produces case spam.\n\n**5. For high-stakes exams only: per-student answer variation.** Detection findings leak instantly — once one student says \"SSH brute force from 10.10.20.10 against ubuntu-app-01,\" that answer is worth nothing. The only fix is a per-student marker inside the fired attack (a distinct targeted username, a distinct SQLi URI, a distinct wordlist entry) so the student must read *their* alert. The runner already parameterises origin/target and builds queries from `match:` field paths, so a `marker:` field fits the contract. **Cost: one attack run per student, serialised on one kali-01.** Fine for a 90-minute practical; impossible during a live shift. Treat this as a hypothesis to prototype on one scenario before committing the catalogue.\n\n**6. Collusion checks as an instructor review queue, never automatic penalties.** Port KYPO's heuristics: time proximity (two correct submissions within ~2 minutes), minimal solve time, **no-commands** (a claimed finding with no console or indexer activity behind it — pairs directly with auditd/indexer audit evidence), forbidden commands. **Skip \"location similarity\" entirely** — every student arrives through the same Guacamole front door, so it is 100% false positives by construction.
