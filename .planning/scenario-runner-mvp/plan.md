## Goal

"Done" means an instructor, from the jumpbox control node, can run the full teaching loop for
**two** scenarios (`ssh-bruteforce`, `web-sqli`) and have each step machine-prove itself:

1. `task scenario:list` prints the catalogue (id, attacker→target, ATT&CK id, expected rule, latency budget) from a single committed `ansible/scenarios.yml`.
2. `task scenario:run -- ssh-bruteforce` (and `-- web-sqli`) starts kali-01 (10.10.20.10, vmbr2), runs the attack across fw-01 against ubuntu-app-01 (10.10.10.30, vmbr1), and the attack **reliably fires a built-in Wazuh rule** (no custom rules for the MVP).
3. `task scenario:verify -- <name>` queries the **Wazuh indexer** `_search` on `127.0.0.1:9200` ON wazuh-01, proves the expected `rule.id` + fields fired within the per-scenario latency budget (poll/retry), and exits non-zero with a diagnostic if it did not.
4. A student investigates in the Wazuh dashboard; the alert evidence is durable.
5. `task scenario:reset -- <name>` rolls back **only** the target VMs (106 ubuntu-app-01, 108 kali-01) to a deliberate `scenario-baseline` snapshot, repairs clock + agent, and PRESERVES the SIEM/control-plane (104 wazuh-01, dc-01, fw-01, jumpbox are never touched) so the fired alerts survive for grading.
6. `task scenario:snapshot` takes the one-time `scenario-baseline` on the targets, deliberately, AFTER instrumentation is proven.

Verifiable end state: run → verify passes for both scenarios; reset restores a clean-but-instrumented
target while the indexer still holds the alert history; every new YAML/HCL/shell artefact passes the
existing pre-commit gates.

The standing scenario allow must sit **immediately before** it (~line 305). fw-01 is reachability-only in Ansible (`inventory/hosts.yml:45-51`); OPNsense is configured by API/config.xml, not a playbook.
- **Snapshot/reset machinery to imitate:** `scripts/learner-snapshot.sh`, `scripts/learner-reset.sh` — run `qm` ON the host, disk-only (NO `--vmstate`), stop-before-snapshot, rollback-then-explicit-`qm start`, post-rollback repairs (`chronyc makestep` / `w32tm`, restart `wazuh-agent`), the `assert_vm_belongs_to_learner` NAME guard, `--dry-run`, colored `info/ok/warn/die`. Wired to Taskfile by scp-to-`/tmp` + `ssh -t "$LAB_HOST_SSH" 'sudo bash /tmp/...'`.

- **Roles house style:** `ansible/roles/README.md` + the three existing roles — minimal (`tasks`/`defaults`/`handlers` only), namespaced vars, restart via handler (not inline), end with an `assert`.

Live target facts (from `lab.yaml`): ubuntu-app-01 = VMID 106, reprovisioned/full clone, vmbr1,
`started: true`, 40G. kali-01 = VMID 108, **linked** clone, vmbr2, **`started: false`**, 40G.
No `lab.yaml` change is required (no new VMs) → the offline `tofu` tests are unaffected but still run as a guard.

Hard constraints (CLAUDE.md): verify on the host, never assume; kill any long process by captured PID
(none expected here); secrets policy (only 10.10.10/20/99 committable; no real mgmt IP/creds);
pre-commit gates gitleaks + yamllint + `tofu fmt`/`packer fmt` must pass; `tofu -chdir=tofu test` is
only strictly required if `lab.yaml` changes (it does not).

**Decisions baked in — do not re-open:** verify hits the indexer `_search` (not the rules API);
ONE standing fw-01 allow rule (live + reconciled into the template), no per-scenario firewall changes;
`scenario-baseline` is one deliberate disk-only snapshot on 106 & 108 taken AFTER instrumentation,
`scenario:run` never auto-snapshots; reset rolls back only 106 & 108, wazuh-01 (104) is never touched;
built-in ruleset only, `local_rules.xml` left untouched.

## Waves

Ordering constraint that spans the plan: the **`scenario-baseline` snapshot (Wave 4) must be taken
only after Wave 2 instrumentation and Wave 3 run→verify are proven**, so a rollback yields a
clean-but-instrumented target (nginx localfile present, kali tooling present, disk-grow complete).
Waves 1–3 therefore run against the live, un-snapshotted targets; the reset path is not usable until
Wave 4 takes the baseline.

### Wave 1 — Scenario contract + verify harness (build the core capability first)

Rationale (codex Top-3 #1): a testable detection contract and verification command come before any
attack tooling. Wave 1 is provable against a **manually-triggered** alert.

Tasks:

1. **`ansible/scenarios.yml`** (new, yamllint-clean). Catalogue seeded with both scenarios. Per entry:
   `id`, `title`, `attack` (ATT&CK id), `origin` (kali-01), `target` (ubuntu-app-01), `objective`,
   `prereqs` (free-text), `reset_targets` (`[106, 108]`), and an `expected_alerts` list. Each expected
   alert carries: `rule_id`, `match` (map of indexer field → value, e.g. `data.srcip: 10.10.20.10`,
   `agent.name: ubuntu-app-01`), `min_count`, `latency_budget_seconds`. Rule ids recorded as the
   proposal's **expected** values (ssh: 5710/5712/5720; web: 31103/31106) — flagged as
   confirm-on-host, not asserted blind.
2. **`ansible/inventory/group_vars/all.yml`** (edit): add `wazuh_indexer_port: 9200`,
   `wazuh_indexer_user` (env `MUTASPACE_WAZUH_INDEXER_USER`, default `admin`), `wazuh_indexer_password`
   (env `MUTASPACE_WAZUH_INDEXER_PASSWORD`, `default=Undefined`) — mirroring the existing `wazuh_api_*`
   lines exactly, with the same secrets-from-env comment. No secret value committed.
3. **Verify mechanism**: a `verify` play in **`ansible/playbooks/75-scenario-run.yml`** targeting
   `hosts: wazuh_manager`, `become: true`, tag `verify` (copying the 70-detections on-manager pattern).
   It loads `scenarios.yml` (`include_vars`/`lookup`), selects the entry by `scenario_id` (passed via
   `-e scenario_id=<name>`), and for each `expected_alerts` item issues a POST to
   `https://127.0.0.1:{{ wazuh_indexer_port }}/wazuh-alerts-*/_search` (`validate_certs: false`,
   basic auth from `wazuh_indexer_*`, `no_log: true`) with a bool query on `rule.id` + the `match`
   fields + `@timestamp >= scenario_run_started_at`. Poll/retry (`until` + `retries`/`delay`) until
   `hits.total >= min_count` or the `latency_budget_seconds` is exhausted; then `assert` with a
   diagnostic fail_msg (rule id, fields, window, observed count).
4. **`Taskfile.yml`** (edit): add `scenario:verify` in a new `scenario:` block (mirror `learner:`
   precondition guards — assert `{{.CLI_ARGS}}` names a scenario; assert indexer creds present). It
   runs `ansible:run`-style `ansible-playbook -i {{.INVENTORY}} playbooks/75-scenario-run.yml
   --tags verify -e scenario_id={{.CLI_ARGS}}`.

Done = `task scenario:verify -- ssh-bruteforce` runs end-to-end and correctly reports PASS/FAIL.

Verification:
- `yamllint ansible/scenarios.yml ansible/playbooks/75-scenario-run.yml` clean.
- On jumpbox-01 (10.10.10.5), export indexer creds from `.secrets/wazuh-passwords.txt`; manually
  trip a built-in alert (a handful of failed SSH logins to 10.10.10.30 by hand), then
  `task scenario:verify -- ssh-bruteforce` PASSES.
- Negative control: run verify against a scenario/rule with no recent activity and confirm it FAILS
  cleanly after the latency budget (proves it is really querying, not always-green).

### Wave 2 — Target instrumentation & prerequisites

Make the two built-in detections physically possible and give kali its tools. Nothing here is
snapshotted yet.

Tasks:

1. **nginx access-log localfile (the web-sqli blocker).** New role
   **`ansible/roles/wazuh_localfile_nginx`** (house style: `tasks`/`defaults`/`handlers`, namespaced
   vars, restart-agent handler, closing `assert`). It adds a second `<ossec_config>` block with
   `<localfile><location>/var/log/nginx/access.log</location><log_format>apache</log_format></localfile>`
   to `/var/ossec/etc/ossec.conf` on ubuntu-app-01, idempotently (guard on the location string, same
   append-a-block idiom used for the Windows Sysmon channel in `60-endpoints.yml:215-256`), and
   notifies a `Restart wazuh-agent` handler. Wire the role into **`60-endpoints.yml`** on the
   ubuntu-app-01 play so it is part of the standard instrumented baseline (not a scenario-time action).
2. **kali-01 attack tooling.** In `75-scenario-run.yml`, a play/role step (tag by scenario) that
   ensures kali-01 is powered on and `hydra` + `sqlmap` are installed and confirmed (apt, pinned/held
   in kali's rolling style; `command -v hydra sqlmap` assert). Powering kali on is a `qm start 108`
   step — call out that the operator must have kali running (see the power-on note below).
3. **The one-time fw-01 standing allow rule.**
   - Live: add ONE narrow standing pass rule on the running fw-01 via OPNsense API/console:
     interface opt1 (vmbr2), source opt1 net, destination host **10.10.10.30**, proto **tcp**,
     dports **22,80** (port alias, or two sibling rules if simpler), placed **before** the
     `block opt1→lan` rule. Do NOT rebuild/re-clone the live gateway.
   - Reconcile: add the identical rule into
     **`packer/opnsense-267/config/config.xml.pkrtpl.hcl`** immediately above the block rule
     (~line 305) so a future template rebuild keeps it. Comment it as the scenario allow.
   - Document the one-time live change in the scenario doc (Wave 5) and `docs/iac/resume-here.md`.
4. **Manager-health / rule-collision gate** (codex "Missing" item): a lightweight check (reuse the
   70-detections auth + `GET /manager/status` or `manager/configuration/validation`) asserting the
   manager is healthy and analysisd loaded before scenarios are declared runnable. `local_rules.xml`
   stays untouched (no reload risk) — the gate just proves health.

Verification:
- On the host: `grep '^template: 1' /etc/pve/qemu-server/108.conf` context aside — confirm kali-01
  is up (`qm status 108`), `hydra`/`sqlmap` present over SSH.
- On ubuntu-app-01: `grep nginx/access.log /var/ossec/etc/ossec.conf` present; `wazuh-agent` running.
- On fw-01: the allow rule is present and ordered before the block (OPNsense UI/`pfctl -sr`); a manual
  `nc -vz 10.10.10.30 22` and `curl` from kali reaches the target, while other opt1→lan traffic is
  still blocked.
- `packer validate` for opnsense-267 still passes (templatefile renders); rendered config XML is
  well-formed. `packer fmt -check` clean.
- `yamllint` clean on the edited playbook/role.

### Wave 3 — The two scenarios end-to-end (run → verify)

Tasks:

1. **`75-scenario-run.yml` attack plays** (tag-selected by scenario, `-e scenario_id=<name>`):
   - `ssh-bruteforce`: from kali-01, `hydra -l <user> -P <small wordlist> ssh://10.10.10.30` — a
     bounded burst sufficient to cross the built-in ≥N-failures/120s threshold (T1110). Record a
     `scenario_run_started_at` timestamp fact for the verify window.
   - `web-sqli`: from kali-01, `sqlmap`/crafted `curl` of `UNION SELECT` / `' OR 1=1` patterns against
     `http://10.10.10.30/` (T1190), producing access.log lines the new localfile forwards.
   The run play sets the timestamp, runs the attack, then chains into the Wave-1 `verify` play.
2. **`Taskfile.yml`**: add `scenario:list` (prints the catalogue from `scenarios.yml`) and
   `scenario:run` (mirrors `learner:` guards; runs the attack tags then verify). `scenario:run`
   **never** snapshots (decision 3).

Confirm-on-host the EXPECTED rule ids before declaring done (CLAUDE.md — do not assert blind): read the
indexer/dashboard to see which of 5710/5712/5720 (ssh) and 31103/31106 (web) actually fire, and pin the
catalogue's `expected_alerts` to the observed ids.

Verification:
- `task scenario:run -- ssh-bruteforce` → verify PASSES; the fired rule id/srcip/agent visible in the
  Wazuh dashboard.
- `task scenario:run -- web-sqli` → verify PASSES (proves the Wave-2 localfile works end-to-end).
- Re-run each twice to show class-style repeatability (codex reliability bar).
- Requires kali-01 powered on — call the operator to confirm `qm status 108` = running.

### Wave 4 — Snapshot roles + reset + reset-correctness

Only now is the baseline taken, against proven-instrumented targets.

Tasks:

1. **`scripts/scenario-snapshot.sh`** (new; copy `learner-snapshot.sh` line-for-line, retarget).
   Fixed target set **{106 ubuntu-app-01, 108 kali-01}**; snapshot name **`scenario-baseline`**
   (distinct from learner `baseline`); disk-only (NO `--vmstate`); stop-before-snapshot; `--dry-run`
   + colored idiom preserved. **Reuse the NAME guard** — assert VMID 106 is named `ubuntu-app-01` and
   108 is `kali-01` (adapt `assert_vm_belongs_to_learner` to a static role→name map) so a mis-numbered
   edit cannot snapshot the wrong VM. wazuh-01 (104) / dc-01 / fw-01 / jumpbox are not in the set.
2. **`scripts/scenario-reset.sh`** (new; copy `learner-reset.sh`, retarget the same set + name).
   Rollback-then-explicit-`qm start`; post-rollback repairs (`timedatectl set-ntp true; chronyc
   makestep`; restart `wazuh-agent`) exactly as the learner script; confirmation prompt; `--force`
   for automation; `--dry-run`. **Never** rolls back 104.
3. **`Taskfile.yml`**: add `scenario:snapshot` and `scenario:reset` mirroring `learner:snapshot`/
   `learner:reset` (scp to `/tmp`, `ssh -t "$LAB_HOST_SSH" 'sudo bash /tmp/...'`, `LAB_HOST_SSH`
   precondition). `scenario:reset -- <name>` passes the scenario id through for messaging; the reset
   target set is fixed to 106 & 108 regardless.
4. **Reset-correctness checks** (codex "Missing" item) folded into `scenario-reset.sh` post-run and
   documented: after rollback assert per target — power state running, name-guard match, `wazuh-agent`
   reconnected (`client.keys` non-empty / manager `agent_control -l`), clock synced; and assert
   **artifact absence** on the disk-rolled targets (the attack-window auth.log / access.log lines are
   gone) WHILE the indexer on wazuh-01 still holds the alerts (evidence retention). Record a baseline
   alert-count expectation.
5. **Optional (documented, NOT automated):** a deliberate "full baseline / clear history" procedure
   (re-take `scenario-baseline`, and separately how one would reset the SIEM) lives in the doc, off the
   automated MVP path.

Verification:
- `task scenario:snapshot` (after Waves 2–3 pass) → `qm listsnapshot 106` and `108` show
  `scenario-baseline`; 104 has none from this.
- Full loop: `task scenario:run -- ssh-bruteforce` → verify PASS → `task scenario:reset -- ssh-bruteforce`
  → targets back up, clock/agent repaired, attack artifacts gone on disk, **alert still queryable in the
  indexer** (run `scenario:verify` against the historical window to prove retention). Repeat for web-sqli.
- `--dry-run` on both scripts shows the correct VMIDs and refuses on a name mismatch.
- Confirm on host that wazuh-01 (104) was never stopped/rolled back during a reset (`qm status`,
  snapshot list unchanged, dashboard uptime unbroken).
